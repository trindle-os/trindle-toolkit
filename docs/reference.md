# Trindle Toolkit reference

The full reference for the Trindle Toolkit: what changes, every widget, and the parts a program paints for itself. For a first program, start with [the guide](guide.md). For what the toolkit is and how to build it, see [the README](../README.md).

## Changes

The toolkit changes whenever the programs built on it need it to. No part is promised stable, so a program should pin the exact version. The session lock (`Kind::Lock`, `Display::lock_session`, `SessionLock`) has only been run against a stand-in compositor, never a real one.

## Widgets

All are functions in `widget`, and each returns a `Node<M>` where `M` is your `Msg`. Settings such as `.padding(24.0)`, `.gap(16.0)` and `.on_press(msg)` are methods on the node.

## Guides, checks and releasing

One short guide for each widget, with a picture, is in [docs/widgets](widgets/README.md). Short guides for a whole kind of job, with compiled examples, are in `docs/guides`: [buttons](guides/buttons.md), [choices](guides/choices.md), [typing](guides/typing.md), [lists](guides/lists.md), [layout](guides/layout.md), [progress](guides/progress.md) and [your own widget kind](guides/custom-widgets.md). Checks that guard the looks: `src/gallery/states.rs` draws every part in every state in every look and fails if one is missing, empty or runs outside the window; `src/gallery/golden.rs` compares small pictures with those in `tests/golden` (refresh with `TRINDLE_GOLDEN=refresh`, then look at them before committing); `words.png` is the one with words in it, drawn by `text::built_in_fonts_only()`, which a program calls once, before its first window, to have every word set in the built-in Noto fonts with the usual hinting whatever is installed and whatever fontconfig says, for a picture that is the same on every computer; `src/fuzz_tests.rs` throws random keys and pointer moves from a fixed seed; the gallery's budget test fails when painting becomes many times slower. `trindle-lang-check --missing [language]` lists the words a language lacks. [RELEASING.md](../RELEASING.md) is the release checklist.
## Pages, panels and frames

`nav::stack(names, current, choose, page)` puts a strip of the pages' names over the page shown; `nav::stack_beside(items, current, choose, page)` puts them as places down a side bar (`--trindle-sidebar-width`, 240) instead. `nav::page_key(input, current, count)` gives the page Ctrl+Page Down, Ctrl+Page Up, Ctrl+Tab and Ctrl+Shift+Tab move to, round the ends, for a program's `intercept`.

`nav::History` keeps the pages a navigation view went through (`push`, `back`, `home`, `current`, `can_go_back`, `trail`); the first is never left. `nav::nav_view(name, back, page)` shows a page under a bar with its name and, when `back` is given, a Back button that sends it, as Escape does. `nav::back_key(input)` is true for Alt+Left, the keyboard's Back key and the mouse's back button.

`nav::split_view(width, side, content, name, showing, back)` puts a side bar beside its content. The program passes its window width from `App::resized`; below `--trindle-split-narrow` (600 points, `nav::is_narrow`) only one side shows: the side bar, or while `showing` the content as a navigation view whose Back sends `back`. `nav::drawer(page, panel, open, edge, width, shut)` lays a panel over a page from either `Edge`, `--trindle-drawer-width` wide (320) but always leaving `--trindle-drawer-room` (56) of the page, which can still be used; it floats on a card with a Close the panel button, and Escape shuts it too. That is both the overlay side bar of a narrow window and a context drawer. `nav::bottom_sheet(page, panel, open, shut)` is the same along the foot, across the whole width.

`pages::preferences(width, pages, current, choose, showing, back, page)` is a preferences window: a split view of the pages' names beside the `settings::setting_page` shown. `pages::status_page(icon, title, words, action)` is a page with nothing else to show (an empty folder, no results), in the middle of its room with a large quiet icon (`--trindle-status-icon`, 96) and at most one action; `pages::welcome_page(icon, name, words, start_words, start)` is one with the main action. `pages::about_page(key, &About)` shows a program's icon, name, version, sentence, website, credits, licence and copyright.

`frames::frame(name, inner)` is a card under its name. `frames::fixed(items)` puts each item at its own place in points. `frames::badged(inner, badge, Corner)` lays a badge (a count, a dot) over a corner, on purpose, taking no room. `frames::revealer(inner, share)` fades `inner` in as `share` goes from 0 to 1 (move it with `motion::tween`, which jumps for anyone who asked for less movement); at 0 it is gone, out of the keyboard's and the screen reader's way. `frames::dots(count, current, choose)` is a dot for each page (`--trindle-dot`, 8, in a target of `--trindle-dot-target`, 24), each read as "Page 2 of 5" and pressed on the current one; `frames::pager(pages, width, at, choose)` slides pages of one width to page `at` over their dots.

## A grid of icons you paint (folders, pictures)

`icongrid::IconGrid` holds how many tiles there are, which are chosen (`selection`, a `Selection`) and how far down it is scrolled. Tiles are `--trindle-icon-tile` square (112) with the icon `--trindle-icon-tile-icon` (48) over the name, the sheet's gap apart, as many across as fit. `tile_rect`, `at`, `columns`, `height`, `scroll` and `reveal` place them; `pointer(event, mods, size)` and `key(input, size)` take the drawing's pointer and keys; `said(size, name)` gives the screen reader the tiles in sight, each with its name and whether it is chosen; `paint_icons(canvas, pen, &grid, hover, keys, tile)` paints them.

`Selection` is the many-chosen model any list or grid can share: a press chooses one, Ctrl+press adds or takes away, Shift+press chooses the run from the last one pressed; the arrows, Home and End move and choose (Shift chooses the run, Ctrl only moves), Space chooses (Ctrl+Space adds or takes away) and Ctrl+A chooses all. A press between tiles lets all go and starts a rubber band: dragged, it chooses every tile it touches (with Ctrl or Shift held, as well as what was chosen), washed in the highlight at `--trindle-selection` strength. `Selection::band` is the same for a list a program paints. The ready-made `list(..).many(..)` has no band yet.

## Kinetic scrolling

A scrolling area swiped by a finger, or flicked on a touchpad, coasts on once let go at the speed of its last tenth of a second, slowing by `--trindle-fling-friction` (4, a share of its speed a second) until it stops or reaches its end. Putting a finger down, pressing, a key or a wheel's notch stops it at once. Nothing coasts for anyone who asked for less movement, or after a slow drag. A touchpad's lift is the compositor's axis stop, passed on as a scroll of nothing (`Input::Scroll` with `x` and `y` 0 and `steps` false).

## Zooming, panning and cropping a picture you paint

`zoom::View` keeps where a picture lies in your `drawing`: shown whole and centred (never enlarged past its own size), or zoomed up to 16 times. `wheel(lines, about)` takes the lines from `on_scroll` (remember the last hover point as `about`), `zoom_in`, `zoom_out`, `actual` and `fit` are for buttons and keys, and a zoom keeps the place under the pointer where it was. Give the drawing's pointer to a `zoom::Drag` and a held press moves a zoomed picture. Paint the picture into `View::content_rect`; `to_content`, `to_screen` and `rect_to_screen` change places between the drawing and the picture.

`View::turn_right` and `turn_left` turn the picture by quarters and show it whole; `turns` says how many (0 to 3). Every place and box the view gives is then in the turned picture's units: paint `picture::turned(&img, view.turns())` (keep the turned copy, it is a new picture) into `content_rect`, and turn a crop box with it (`Crop::turn_right`, `turn_left`). `picture::cropped(&img, crop.rect())` cuts the chosen part out in whole pixels.

A fling keeps the picture moving: give the drawing's pointer to `Drag::pointer_at(view, event, now)` (`pointer` takes the time itself) and a quick release of a zoomed picture sets it gliding. While `Drag::gliding` is true, call `Drag::glide(view, dt)` each frame (it says whether the picture moved, so repaint); it slows by itself, stops at the picture's edge, a new press catches it, and with reduced motion (`motion::reduced`) there is no glide. `View::pan_by` now says how far it really went.

`crop::Crop` is a box inside the picture's bounds, in the picture's units, with eight handles and a body. `set_aspect(Some(1.0))` (or 4/3, 16/9) holds the ratio through every pull; `None` lets it go free. `crop::Gesture` takes the drawing's pointer and the `View`, so handles are pulled correctly while zoomed, and `Gesture::cursor` gives the arrow to show. `grow` and `move_by` are for the keyboard. Paint it with `crop::paint_crop(canvas, pen, picture_rect_in_points, box_in_points)`; handles are 12 points with a 24 point grab, as WCAG 2.2 asks.

## Pictures and files on the clipboard

Besides text (`Window::copy`, `paste`), a window puts and reads two more kinds of thing, each under the kind other programs use. `copy_image(png)` takes a picture already encoded as PNG (`image/png`; bytes that do not start as a PNG, or over 64 MiB, are refused and it says false). `copy_files(paths)` offers whole (absolute) paths as `text/uri-list`, the file managers' `x-special/gnome-copied-files` copy note and plain paths, so a file manager can paste them. `clipboard_has()` says whether the clipboard holds text, a picture or files (`OnClipboard`). `paste_image(call)` hands over the PNG bytes once all have come (checked to start as a PNG, at most 64 MiB, 15 seconds), and `paste_files(call)` the paths of a `text/uri-list` that is wholly files of this computer (`dnd::parse_uri_list` rules). Nothing is read on the window's thread. Where the compositor does not announce the copy, it goes through the clipboard protocol every Trindle program may use, as text does. Only the parts that need no compositor are tested; the round trip through a real clipboard has not been run. `ui::App` has no hook for these yet, so a program calls them on its `Window`.

## Small jobs beside Trindle

`common::plumbing` has `write_private(path, bytes)` (a file replaced whole, mode 0600, flushed, never half there), `Ini` (`Ini::read(path)`, `get`, `get_bool`, `get_list`, `set`, `write`; comments are not kept), `notify_line(path, summary, body)` for a plugin's `notify.jsonl`, `file_uri`, `open_folder(&bus, &lp, folder, done)` (the file manager's service, else `xdg-open`) and `decode_in_background(path, done)` (this one needs the `ui` feature). `common::windowless::Windowless` is the Wayland setup for a program with no window: `open()` connects, finds the registry and the seat, and `dispatch_for(state, wait)` waits on the desktop for a time. The clipboard watcher in `common::selection` is built on it.

## Keyboard shortcuts

`shortcuts::Shortcuts` holds chords and what they do: `bind("Ctrl+Shift+C", Action::Copy)` (gives back an action it displaced, or the action if the chord cannot be read), `find(&input)` from a key press (a letter matches with or without Shift making it a capital), `chord_of(&action)` and `all()` for a help page, and `Chord::text()` writes one for a menu with the modifier names from the language file.

`clashes()` lists the bound chords the toolkit takes first, with `shortcuts::Kept::Window` (Tab, Shift+Tab, Escape, Menu, Shift+F10) or `Kept::Typing` (Ctrl+A, C, X, V, Z, Shift+Z and Y while a text box has the keyboard); `Chord::kept()` says the same of one chord. Keys whose names are words (Page down, Enter, Escape, the arrows) are written from the language file. `page(says)` is a page listing every shortcut, what it does in the program's words from `says` beside its keys, with a line in the problem tone under one that clashes.

## Undo and redo across a window

`history::History<T>` keeps the steps a program has done, each a `T` it knows how to reverse: `push(step)`, `typed(place, step, now, join)` (typing in one box less than a second apart joins onto the last step), `undo()` and `redo()` (each gives the step to reverse or repeat), `can_undo`, `can_redo` and `clear`. `Ui::on_undo(undo, redo)` sends `undo` for Ctrl+Z and `redo` for Ctrl+Shift+Z or Ctrl+Y wherever the keyboard is, except in a text box that still has steps of its own that way, so the box undoes its own typing first and the window carries on after. A text area (`editing::area::TextArea`) passes the keys on the same way once its own steps run out (`Pane::passes`).

## Two-finger gestures

`pinch::Pinch` follows the fingers on a window: feed it every touch event and, while two are down, each move gives a `Twist` with `scale` (what the distance between them was multiplied by), `turn` (radians, clockwise), `centre` and `moved`. A third finger is ignored; lifting either ends it. For a picture, `view.zoom_to(view.scale() * t.scale, about)` and `view.pan_by(t.moved.0, t.moved.1)` from `zoom::View`. `active()` says two fingers are down, or a touchpad pinch is under way, so one-finger work can wait.

A touchpad's pinch comes from the compositor's pointer gestures as `Input::PadPinch(Twist)`, the change since the last one about the pointer, and ends with `Input::PadPinchEnd { cancelled }`; on cancelled, put back what the pinch changed. `Pinch` takes these too, so one `Twist` handler serves the touch screen and the touchpad. A compositor without pointer gestures sends neither.

## An emoji page

`file_page::FilePage::new(purpose, folder)` is a file chooser drawn as a page in the window, for a program that wants one of its own rather than the desktop's (`chooser` asks the portal). `Purpose` is `Open`, `Save` or `Folder`. `view(title, Msg::Files, Msg::Cancel)` is a `dialog` page: the path as pressable parts, Up, a switch for hidden files, the folders and files (folders first, sizes at the end of each row), a name box when saving, and the answer. Arrows choose a row, Enter or a double click opens it: a folder is gone into, a file is the answer when opening. `update(step)` reads folders as it goes and gives back `Some(path)` once the answer is final; an answer that cannot be taken (nothing chosen, an empty name or one with a slash, a folder that cannot be read) shows red words under the list. `font_page::FontPage::new(family, size)` is the same for fonts: `view(&fonts.chooser(), title, Msg::Font, Msg::Cancel)` shows a box to find a family by name, the families (monospace ones marked), the size (6 to 96) and sample words drawn in the chosen font; `update` gives back `Some((family, size))` on the answer, or on Enter in the list.

`emoji_picker::emoji_page(search, typed, pick)` is a page of 176 emoji in eight groups (faces, hands, animals, nature, food and drink, travel and places, objects, symbols) with a box that finds them by name; `pick` is given the emoji pressed, and each is told to a screen reader by its name. The names are in the English language file; a language that has not written a name shows the English one.

## Following the desktop's look

`desktop::follow(&bus, &lp, changed)` reads the settings portal now and again whenever the person changes it, and tells `changed` a `Look`: `light` (None for no preference), `accent` (`accent_css()` goes straight to `Theme::new`), `more_contrast` and `reduce_motion`. ## Notifications and a tray icon

Every bus call (connecting, listening, sending, replying, serving) waits on the bus on the calling thread for at most 5 seconds, so a stalled bus daemon makes a window pause that long and then fail rather than freeze for good; call from a worker thread where that matters.

`notify::Notifier::new(&bus, heard)` sends freedesktop notifications: `send(&lp, &Note::new(app, summary, body), replaces, done)` gives the number back, a `Note` may carry action buttons, an urgency and a timeout, and `heard` is told `Heard::Action` and `Heard::Gone` (expired, dismissed or closed). `notify::Tray::new(&bus, &lp, id, title, icon_name, click, done)` puts a StatusNotifierItem in the panel's tray: `click` hears `Activate`, `Secondary`, `Menu` (draw your own menu there) and `Scroll`, and `set_icon`, `set_title` and `set_status` change it. Both are tested against a private bus with stand-in services, not against a real panel.

## Locking the session (ext-session-lock-v1)

`Display::has_session_lock()` says whether the compositor offers it. `Display::lock_session()` asks for the lock and gives a `SessionLock` (None if it is not offered, or this program already holds one). Then open one `Kind::Lock { screen }` window for each name in `Display::screens()`; the compositor sets its size, and it takes the keyboard like any lock surface. `display.on_lock(|phase| ..)` and `SessionLock::phase()` tell `LockPhase::Asked`, `Locked` (every screen is covered), `Finished` (the compositor ended the lock, or would not give it) and `Unlocked`. `SessionLock::unlock()` sends `unlock_and_destroy` and waits for the compositor to handle it; it is refused before `Locked` and after `Finished`, where `destroy()` is the only way out. Dropping a `SessionLock` leaves the session locked, as the protocol means it to. The rules are kept in a plain `Sequence` with no connection in it. No looks come with it: what the surfaces show is the painter you give `open`.

Tested: the order of requests and the phases (unit tests), and the whole path against a stand-in compositor on a socket pair (ask, surface, configure and acknowledge, locked, unlock). Not tested: any real compositor (what a real one does with a surface that is late, a second client's lock, outputs that come and go while locked), input on a lock surface, and a screen that appears after the lock is made, for which you open another `Kind::Lock` window yourself.

## Window states, dialogs and icons

On an ordinary `Window`: `set_fullscreen(bool)`, `set_maximised(bool)`, `minimise()`, `limit(least, most)` (sizes in points, `None` for no limit), `set_child_of(Some(&parent))` to keep a window above another of yours, `set_modal(true)` to make that child a dialog that blocks its parent, and `set_icon(name, pixels)` for the theme icon `name` plus a square picture for a compositor with no such icon. Each does nothing on a panel, and `set_modal` and `set_icon` do nothing where the compositor lacks the xdg-dialog or xdg-toplevel-icon protocol. These are checked to build and are not tested against a real compositor.

## Keeping a window's shape and what was open

`keep::Shape::load(app_id)` gives the size (in points) and maximised state the program last kept, None the first time: open the window at `shape.size`, then `shape.apply(&window)` maximises it if it was. Before it closes, `shape.note(&window)` and `shape.save(app_id)`; `note` keeps the size from before a maximise, so the window comes back to it when put back. `Window::maximised()` says what the compositor last said. `keep::keep_open(app_id, &items)` keeps what the program had open (paths, addresses, one to a line) and `keep::opened_last(app_id)` gives it back on the next start, which is how a program restores itself after login. Both live in `$XDG_STATE_HOME/<app_id>` (`~/.local/state` when it is unset), written whole and for the person alone; an app id that is not a plain reverse-domain name gets no folder. Where the window sits on the screen is not kept: Wayland leaves that to the compositor.

## One copy of a program

`once::claim(&bus, &lp, name, path, first, later)` claims `name` on the session bus, firmly, so no later copy can take it. The first copy runs `first`, where it opens its window and calls `once::serve_window(&bus, path, &window)`. A second copy hands the first the activation pass it was started with, so the first may come forward (`Window::raise`), then runs `later`, which hands over whatever else it was asked to open and ends. If the first never answers (still starting, or stuck), the later copy asks three times in two seconds and then starts as the first, so a press is never lost. `once::serve` is the same for a program with its own idea of what coming forward means. Tested on a private bus with two copies.

## Drag and drop with other programs

Taking: give any widget `on_drop_from_outside(would, take)`. `would` is told what is offered and which `Part` it is over (a row, the gap between two rows, a point on a drawing, or the whole) and answers the `Way` it would take it, or None; the widget under the pointer is lit and the pointer shows the answer. `take` is handed the `Given` (files, text, or `Nothing` with the reason) once it is let go and read, with every rule in `dnd` applied (sizes, counts, time, paths). A text box takes dropped text by itself. A move the program is still working on answers `App::drop_end` with `DropEnd::Later` and calls `Window::drop_done` when it is finished, so the other program removes its copy only then.

Giving: `App::dragging` returns a `Lifted` (files, a label, an icon) while a button holds them; once the pointer leaves the window they are offered to the program under it, as a file list and through the file-transfer portal for sandboxed programs, with a picture at the pointer. The program hears `Input::DragEnded`: `took` is the way the other program took it, with proof every byte was handed over, or None with `short` set when it failed part way; on a move, remove the files only when `took` says so. Tested: every rule in `dnd` by unit tests, the widget side in `ui/outside_tests.rs`, and the whole path between two programs by the ignored `between_programs` tests, which need a headless trindle-compose (`drag_test.rs` says how) and are run by hand.

## Fractional scale and screens of different sharpness

The compositor's fractional scale (wp-fractional-scale-v1 with a viewport) is used when offered, so a window at 1.25 or 1.75 is drawn in exactly that many pixels; otherwise the largest whole-number scale of the screens the window is on. A window moved to a screen of another scale is laid out and drawn afresh at the new one. Tested at 1.0, 1.25, 1.5, 1.75 and 2.0 on the gallery of every control: each part keeps its place in points within 3 points and 3 per cent (each line of text is a whole number of pixels, so lines drift a little down a long page), nothing is squeezed, touching or off the side, a press in points lands on the same switch, the ink drawn grows with the square of the scale, and a window moved between scales is drawn exactly as one opened there (bar the spinner, which turns with the clock). Not tested: a real compositor sending a new scale while a frame is in flight.

## Keeping the screen awake, and hearing the lock

`Window::keep_awake(true)` stops the screen dimming, locking or sleeping while that window shows, as a video player does while it plays; `keep_awake(false)` lets it again, and closing the window does too. It returns false where the compositor lacks idle-inhibit-unstable-v1; `kept_awake()` says whether it is on. The compositor honours it only while the window can be seen. `locked::on_locked(&Bus::system(&lp)?, &lp, told, done)` finds this program's login session and tells `told` true when it is locked and false when it is unlocked, starting with how it is now, from logind's `LockedHint`; `done` hears the `Listen` to keep, or None with no logind. It is heard once the locker has the screen, too late to hide anything first. Tested against a stand-in logind on a private bus, and the keep-awake request only to build.

## Portals: choosing files, a screenshot, the camera, opening an address

`chooser::open`, `open_many`, `open_folder` and `save` ask the file chooser portal. `portal::screenshot(&bus, &lp, interactive, done)` gives the path the portal saved a screenshot to. `portal::open_uri(&bus, &lp, uri, ask, done)` opens a web or mail address in the person's chosen program, and `portal::open_file` hands the portal an open file (not its name, so it works from a sandbox); `ask` lets the person choose the program now. `portal::camera(&bus, &lp, done)` asks for the camera and, once allowed, gives a PipeWire connection that reaches only the cameras. The parent window is not given, so the portal's window is not tied to yours. Tested against stand-in portals on a private bus.

## Desktop entries: launcher, open with, defaults and autostart

`entry::Entry::new(app_id, name, &[program, args..])`, with `kinds` (file kinds such as `text/plain`), `schemes` (addresses such as `mailto`), `icon`, `comment` and `unlisted`, is the program's desktop entry. `install()` writes it to `$XDG_DATA_HOME/applications/<app_id>.desktop`, which puts the program in the desktop's list and in "Open with" for those kinds; Exec gets `%F` for files or `%U` for addresses, and every argument is quoted as the format asks. `entry::make_default(app_id, &kinds)` makes it the person's default in `mimeapps.list` (ask them first; comments in that file are not kept), with `entry::scheme_kind("mailto")` for an address handler. `entry::default_for(kind)` reads the person's default and `entry::openers(kind)` lists every program that says it opens a kind, the person's own first. `autostart(true)` writes the same entry to `$XDG_CONFIG_HOME/autostart` to start at login, `autostart(false)` removes it; give `exec` an argument that tells the program it was started that way, so it opens `keep::opened_last` quietly. A value with a line break, an app id that is not a plain reverse-domain name, or a kind or scheme that is not one is refused whole.

## Settings kept in a config folder

`config::Config::new(app_id, version)` is the program's settings folder, `$XDG_CONFIG_HOME/<app_id>/v<version>`, laid out as COSMIC's cosmic-config lays it out: one file per key, the value its text. `get(key)` (None for a missing or unreadable key; `read(key)` gives `Ok(None)` for a missing one and an error for one that cannot be read), `set(key, value)` (written whole, for the person alone), `unset(key)` and `keys()`. `watch(&loop, changed)` tells `changed` the keys set or forgotten by anyone, this program included, until the `Live` is dropped; when news was lost it is told every key. `Config::at(folder)` reads another program's folder, such as COSMIC's. A key that is not a plain name (a slash, a leading dot) is refused. Tested on a temporary folder, with the change heard through the kernel.

## A title bar the program draws

`Window::needs_frame()` says whether the compositor draws no title bar for the window (it lacks xdg-decoration, as GNOME does, or asked the program to); it is known by the first paint. Then call `Shown::frame_shadow()` once and wrap the view in `frame::framed(title, window.frame(), body, act)`: edges all round that resize the window (none while maximised), a bar with the title that moves it, maximises it or puts it back on a double press (two presses within the double-click time and 6 points), and opens the window menu on a right click, and buttons to minimise, maximise or put back, and close. `act` hears a `Framing`; hand `Move` to `Window::begin_move()`, `Resize(edges)` to `begin_resize(edges)` and `Menu(x, y)` to `show_window_menu(x, y)` while the press is handled, and the others to `minimise`, `set_maximised` and closing. `Window::frame()` gives a `Frame`: whether it is maximised, the shadow's room now, and whether the compositor shows a window menu (true unless xdg-shell 5's capabilities leave it out); without one the bar's right click opens the toolkit's own menu (Maximise or Restore, Minimise, Move, Resize, Close). ## A colour, a date and a time to pick

Keep a `picker::ColourBox` (`ColourBox::new(colour)`) in your state, show it with `view(Msg::Colour)` and give each `picker::Edit` back to `update`. ## A table you paint (files, logs, settings)

`table::Table` keeps the columns (`Column::new("Name", 200.0).sortable()`, `.end()` for figures, `.min(..)`), the sort, the chosen row and how far down it is scrolled; it holds no data, so the program says each cell's words when it paints. Paint it in a `drawing` that fills the room: `table::paint_table(canvas, pen, &table, gesture.hovering(&table, tall), |row, column| words)` draws quiet headings with an arrow on the sorted one, then only the rows in sight, the chosen one in the picked colour, and a bar at the right when rows are out of sight.

Give the drawing's pointer (`on_pointer_mods`) to a `table::Gesture` and it says what happened: `Chose` and `Opened` (a second click), `Toggled` (Ctrl) and `Extended` (Shift) for a program that keeps several chosen, `Sorted(column, small_to_large)` when a sortable heading is pressed (sort your rows, then call `Table::set_rows`), `Resizing` and `Resized` while an edge between two headings is dragged (24 points to grab, as WCAG 2.2 asks), and `Fit` for a double click on that edge, which `Table::fit_to(column, &fonts, scale, cell)` answers. `Gesture::cursor` gives the column arrows over an edge. The wheel is `Table::scroll(lines)`; the keys are `step(1, tall)`, `step(-1, tall)`, pages by the rows that fit (`rows_in`), `home` and `end`, each keeping the chosen row in sight. Tell a screen reader with `Node::table_rows(table.said(tall, cell))`: it hears a table with its headings and sort, "row 3 of 12", each cell, and the chosen row as selected, while only the rows in sight are in its tree.

Headings move by drag: past 6 points a press on a heading becomes `Moving(from, to)` (paint the landing line with `table::paint_column_drop(canvas, pen, &table, gesture.moving())`) and letting go is `Moved(from, to)`, with the columns already in their new order and the sort kept on the same column. Each `Column::id` is its place when the table was made, so find a cell's data by `table.columns[column].id`, not by its place. The keys do the same without dragging, as WCAG 2.2 asks: `step_column(-1)` and `step_column(1)` (Left and Right) put the keys on a column, ringed with the keyboard's ring (`--trindle-focus-width`, in the highlight) on the chosen row's cell, or on its heading when no row is chosen, and `shift_column(-1)` and `shift_column(1)` (Ctrl with Left and Right) move that column, giving `(from, to)` as `Moved` does. A press on a cell moves the ring there once the keys are in use. A screen reader is on that cell (or heading) as the table's active descendant.

A column view (a tree table): `Table::set_tree(vec![Branch::closed(0), Branch::leaf(1)])` makes the rows open and close under a parent, set in by their depth in the first column (`--trindle-tree-indent`) behind a control of 24 points square that a press, a double click on the row, Enter, or Right and Left work. `Branch::closed(id)` is a row with children not built yet, `Branch::leaf(id)`, `Branch::opened(id)` one whose children follow it in the list, `.depth(n)` sets how deep; `id` is the program's own number for what the row shows (`table.branch(row)`), so a cell's words are found by it. Opening a closed branch is `Touch::Open(row)` from the gesture or `Table::key`: answer it with `Table::open_row(row, children)`, children given with depths counted from them (0), and only then are their rows made; `Touch::Closed(row)` says an open one was closed and its rows are gone, so the program gives them again on the next opening. A branch given no children becomes a plain row. `Table::key(sym, mods, tall)` is the keys: arrows, Page keys, Home, End, Right (open, or to the first child), Left (close, or to the parent), Enter and Space. A million rows cost no more to paint than the rows in sight, and opening one is a move of the rows below it. The screen reader gets a tree grid with each row's level, whether it is open (and Expand and Collapse actions) and its place among its siblings. `set_rows` ends a tree.

Several rows chosen: set `table.multiple = true` (off by default, so a program that keeps several itself with `Toggled` and `Extended` is unchanged). The table then keeps `picked()` (sorted; `set_picked`, `is_chosen`, `pick_all`) and `chosen` is the row the keys are on. Ctrl click toggles a row (on letting go, as a Ctrl press may begin a band), Shift click chooses the run from the row last clicked, a plain click leaves one; `Table::key` has Shift with the arrows, Home and End extend, Ctrl+A chooses every row and Space toggles the row the keys are on. A band, like the list's, begins in the empty room under the last row, or on a row with Ctrl held, and chooses every row it crosses (Ctrl adds to those already chosen); `Touch::Banded` says the rows changed, and `table::paint_band(canvas, pen, gesture.band(&table, size))` paints it in the selection's strength with an edge, both in the highlight. The screen reader is told the table allows several and which rows are chosen.

Groups: `Table::set_groups(vec![(0, "Today".into()), (12, "Earlier".into())])` puts a heading line over the rows from each first row on, in section words on the band colour. Groups never fold away. Row numbers stay the program's own; `line_of`, `at_line` and `group_of` map between rows and lines, and the screen reader hears each row's group as its description.

Typing in cells: mark a column `.editable()`. A double click on its cell is `Touch::Edit(row, column)`; answer it, or F2 on the chosen row with `edit_column()` (the keys' column when it can be typed in, otherwise the first that can), with `Table::begin_edit(row, column, words)`. Give keys to `Table::edit_key(sym, text, mods)` first: it returns None when no cell is being typed in, `Edited::Typing` while typing (arrows, Home, End, Backspace, Delete, Ctrl for words, Ctrl+A, Ctrl+Z), `Edited::Kept { row, column, text }` on Enter or Tab and `Edited::Dropped` on Escape, `Edited::Copy(words)` on Ctrl+C or Ctrl+X (a cut has already taken the words out; put them on the clipboard) and `Edited::Paste` on Ctrl+V or Shift+Insert (fetch the clipboard and give it to `Table::paste(words)`, which puts it in on one line in place of the selection). A press away from the cell is `Touch::LeftEdit`: keep or leave the words from `Table::end_edit()`. The cell is painted as a typing box with its caret and selection.

## A tab bar you paint (documents, folders, terminals)

`tabs::Tabs` keeps the tabs (`Tab::new("Notes").count(3)`, `.fixed()` for one with no close box), which is chosen and how far along the bar it is. Paint it in a `drawing` with `tabs::paint_tabs(canvas, pen, &tabs, gesture.hovering(&tabs, width), gesture.dragging())`: the chosen tab raised with a line in the highlight, a close box (24 points), the count in quiet words, and, when they do not all fit, the tabs in reach and a button for the rest. The bar's height, the narrowest and widest tab, the close box and that button come from the style sheet (`--trindle-tab-*`).

Give the drawing's pointer to a `tabs::Gesture` and it says `Chose`, `Closed` (close box or middle click; ask about unsaved work, then `Tabs::close`), `Dragging` and `Moved` (the bar is reordered; reorder what the tabs show to match) and `More` (show a menu of every tab and call `Tabs::choose`). A drop from another program onto a tab is `Tabs::tab_at(width, x, y)`. Keys are `step(1, width)` and `step(-1, width)`; the wheel is `scroll`. `open` and `close` keep the chosen tab sensible. Tell a screen reader with `Node::tab_list(tabs.said(width))`: it hears a tab list, "tab 2 of 5", the chosen tab as selected, a Close button in each tab that has one, and can click them.

A tab dragged more than 48 points above or below the bar is `Tearing(tab)` while it is held there and `TornOff(tab)` when let go there; the bar is left as it was. To give it a window of its own, the program builds an `App` for what the tab shows, calls `shown.open_beside(Kind::Window { .. }, size, app)` on its window, keeps the `Shown` it returns for as long as that window stays (in its state or an `Rc`), and then calls `Tabs::close` on the old bar. Both windows read the one style sheet, so they share the theme and change together. Wayland lets no program place a window, so the new one opens where the compositor puts it, not under the pointer. `open_beside` has not been tried against a live compositor here.

## A board of cards you paint (kanban)

`kanban::Board::new(lanes)` keeps the columns (`Lane { title, cards }`, each `Card { title, id }` with the program's own number), the chosen card and how far down it is scrolled. Paint it in a `drawing` with `kanban::paint_board(canvas, pen, &board, gesture.hovering(&board), gesture.dragging())`: each column a card with its name, its cards as boxes 8 points apart, columns 16 points apart, the chosen card in the picked colour, and while a card is dragged a line in the highlight where it would land with the card following the pointer. Give the drawing's pointer to a `kanban::Gesture`: `Chose`, `Dragging(from, to)` and `Moved(from, to)`, places as (column, place), the board already changed to match. The keys do the same without dragging: `step(across, by, tall)` moves the choice (arrows) and `shift(across, by, tall)` moves the chosen card (Ctrl with the arrows), as WCAG 2.2 asks of anything done by dragging. The wheel is `scroll(lines, tall)`. Tell a screen reader with `Node::table_rows(board.said())`: a table whose columns are the board's columns.

## Very long lists

`list(rows, ..)` holds every row as an `Item` and lays them all out, which is fine for thousands but not for millions (`measure_long_lists` in `src/ui/widgets_tests.rs`, run with `--ignored --nocapture`, prints the cost; see MEASUREMENTS.md). For long data use `table::Table`: it holds no rows, only their number, and asks for the words of the cells in sight only, when it paints and when it tells a screen reader. A one-column table with `head_height: 0.0` is a plain long list. `table::tests::a_million_rows_in_groups_cost_no_more_than_the_rows_in_sight` holds a million rows in a thousand groups to asking for no more than the cells in sight.

## A side panel

`panel::side_panel(content, panel, width, shown, Side::End)` puts `panel` beside `content`, `width` points wide when fully in, filling the height, 16 points apart. `shown` runs from 0 (gone: not in the window at all, so the keyboard and a screen reader cannot reach it) to 1, and the content gives up the room as it comes; the panel keeps its width while it slides, so its words do not wrap again. It never folds and never floats over the page. Slide it with `motion::slide(&loop, move |share| shown.change(|app| app.panel = share), || {})`, or `1.0 - share` to slide it away.

## The notice at the foot

`notices::Notices` is the one notice a window shows: `push(words, now)` queues one (the same words as the last are not queued twice), `tick(now)` moves on after `--trindle-notice-stays` (5 seconds) and says whether the view must be built again, `next_wake(now)` says when to call it (`Loop::after`), and `dismiss(now)` takes the shown one away at once. `notices.over(content)` lays the pill over the foot of `content`: the page under it never moves, the pointer passes through its clear band, and a screen reader hears the words politely as they come.

## An outline beside a long page

`outline::outline("outline", &entries, current, Msg::Go)` lists a page's headings (`outline::Entry::new(title, depth, key)`, `key` being the heading widget's key) as places to go, the one being read marked as where you are and deeper headings set in. Put it in a side panel. On `Msg::Go(i)` call `shown.go_to(&entries[i].key)`, which scrolls that heading to the top of its scrolling area; after the page scrolls, `shown.reading(&keys)` gives the heading being read, to pass as `current`.

## A terminal screen

`term::Term::new(cols, rows)` is a terminal's screen and scroll-back fed by a program: `feed(bytes)` takes its output as it comes (a character split between two reads is kept whole), with ANSI colours (the sixteen, 256 and full colour), bold, italic, underline, inverse and strike, cursor moves, erasing, and the cursor shown or hidden; titles and other system commands are passed over and a bell sets `bell`. The sixteen colours are the sheet's `--trindle-term-*`, from the palette, and every colour is moved just far enough to be read on its cell. Paint it in a drawing with `term::paint_term(canvas, pen, &term, size, focused)` (cell size from `cellgrid::cell_metrics`), scroll back with `scroll(lines)` (new output brings the live screen back), change its size with `resize(cols, rows)` and tell a screen reader with `Node::reads(term.reading())`. Keys typed into it are the program's to send on. It is not Fetch Terminal's own, which lives in its own repository.

## High contrast, large text and motion

Six values in a person's own sheet change every window; the sixth, `--trindle-colour-blind-safe: 1`, draws the states (calm, good, busy, bad) and a pie's pieces in Okabe and Ito's colour-universal palette (`--trindle-safe-*`, deeper in the light look) so they can be told apart in deuteranopia, protanopia and tritanopia, and changes nothing else; a program that keeps the choice in its own settings calls `theme::colour_blind_safe(on)`, as it calls `motion::reduce`. No desktop settings portal has a key for it, so the desktop does not set it. A test measures the colours under simulated deficiencies (Machado et al. 2009, CIE76 of at least 15 between any two). `--trindle-large-text` (1 to 2) draws every kind of words that many times larger and makes buttons, typing boxes, rows, menus, tool and word buttons, badges, icons beside words, switches and the tip label as much taller or larger; a test in `src/theme/tests.rs` lists every size of the sheet as growing or staying, and fails when a new one is in neither. `--trindle-high-contrast: 1` holds words and icons to seven to one on every layer they lie on and every edge and line to four and a half, keeping the layers and the highlight; the theme tests hold this for every theme, both looks and every highlight. `--trindle-slide-time` and `--trindle-fade-time` are how long `motion::slide` and `motion::fade` take, on the loop's clock, and `--trindle-reduce-motion: 1` makes every tween instant, as the desktop's own reduced motion does: `desktop::read` and `desktop::follow` hand it to `motion::reduce`, and `settings::LookChoice::theme` raises the contrast when the desktop asks for more.

## A program's own look

`settings::LookChoice` is a program's choice of light, dark or as the desktop (`Shade`) and of its own highlight or the desktop's, kept under `[Look]` in `LookChoice::file(app_id)` (`settings.ini` in the program's folder of the person's settings) with `load` and `save`, which keep the rest of the file. `choice.theme(&desktop_look)` is the look to draw with. `settings::look_page(&choice, &colour_box, Msg::Look)` is a ready settings page for it: the shade as a choice of three and the highlight as a colour picker, with a button back to the desktop's highlight once one of its own is set. Give each `LookEdit` to `choice.apply(edit, &mut colour_box)`, then save and `Shown::set_look`.

## Printing

`print::pdf(tree, theme, Paper::A4)` lays the widgets out at the paper's width inside its margins, paints them with the window's own painting at 144 pixels to the inch over white, and cuts the result into pages of a PDF (at most 200; a longer document is an error, as is a failure to make the pages); `print::print_to(path, ..)` writes it to a file, which any print dialog or `lp` can send to a printer. No new crate is used: the PDF is written by hand, one picture to a page, packed with the toolkit's existing zlib. So the words in it cannot be selected or searched, and a line of words can be cut where one page ends and the next begins. Pass a light theme for paper.

`print::print_on_paper(bus, events, title, tree, theme, Paper::A4, done)` sends those pages to the desktop's printing: the portal shows the person its own page for choosing a printer, and `done` hears whether it went, was called off or could not be done. `portal::print_pdf` does the same with PDF bytes a program made itself.

## A text area (notes, mail, snippets)

`editing::area::TextArea::new(text, Look { font: None, size: 14.0, wrap: true, numbers: false })` is a many-line text box with undo and redo, wrapping, a scroll bar, the right-click menu and the clipboard. Put `area.node("Notes", least_height, Msg::Area)` in the window, where `Msg::Area` wraps an `editing::area::Event`; when the message comes back call `area.handle(event, &window, post)`, which returns true when the words changed (`post` sends a message back for a paste, which arrives a moment late). `text()` and `set_text()` read and replace the words; `pane()` gives the editing area for search marks. `spelling(Some(Rc::new(speller)))` checks the words with a `spelling::Speller` (the same one a text box takes with `Node::spelling`): words it does not know get the wavy line in `--trindle-spelling`, and the screen reader is told of spelling mistakes while one is in sight; `spelling(None)` stops it. The area also offers selected words to a middle click in any program, and a middle click on it pastes the selection. A program with its own selectable words calls `Window::select(text)` the moment the selection is made and `Window::paste_selection(call)` on a middle click (nothing happens where the compositor has no primary selection). A screen reader hears a multi-line text box: the lines from the top of the view, the caret and the selection.

## Rich words, a rich text box, code and help pages

`rich(spans)` is one paragraph of words in several looks, wrapped as one: build the spans with `rich::Span::plain("words")`, `.bold()`, `.italic()`, `.code()` and `Span::link(words, address)`, or read them from a small markup with `rich::parse("Press **Save**, see [the guide](g)")` (`*italic*`, `` `code` ``, a backslash keeps a mark as a letter; inside code a backslash before a backtick or another backslash is an escape, so `` `a\`b` `` is code holding a backtick, and in a link address a backslash before `)` or another backslash is, so `[x](a\)b)` has the address `a)b`; `rich::markup` writes spans back with these escapes. A code span that held two backslashes in a row, written before this, now reads as one). Links are in the highlight's colour and never underlined; `.on_link(Msg::Open)` hears the address of the one pressed. Tab goes from link to link inside the paragraph before leaving it, Enter or Space follows the one with the ring, and a screen reader hears a paragraph with each link as a link it can follow. Right-to-left words stand right to left and a right-to-left paragraph's lines start at the right. A word longer than the line is not broken inside a rich paragraph.

`editing::rich_box::RichBox::new(markup)` is a box of styled words: put `b.node("Note", least, Msg::Rich)` in the window and hand each `rich_box::Event` back to `apply`, which gives `Did::Copy` and `Did::Paste` for the caller to do. Ctrl+B, Ctrl+I and Ctrl+E turn bold, italic and code on or off for what is selected (off when all of it is on), or for what is typed next; typing takes the look of the letter before the caret. `markup()` writes it back to keep; `spans()` gives the looks. Links read in are kept as plain words. A screen reader hears a multi-line text box.

`code::view(text, Lang::Rust, "Code")` shows read-only code with quiet line numbers down the side and words coloured by kind (keyword, type, string, number, comment) from the sheet's `--trindle-code-*` colours, each moved just far enough to be read on the card. `Lang::guess(file_name, first_line)` picks Rust (`.rs`), shell (`.sh`, `.bash`, `.zsh` or a `#!` line naming a shell) or plain; `code::tokens` gives the coloured stretches. Tabs stand for four spaces. It asks for room for its longest line, so put it in a `scroll_x` where lines are long. A screen reader is told every line (as a terminal's lines are told).

`help::markdown(text)` and `help::html(text)` read a help page into `help::Block`s, and `help::view(&blocks, Msg::Open)` shows them with the toolkit's own widgets: `#` or `h1` as a page title, `##` or `h2` as a section, deeper ones as headings, paragraphs and list rows as rich words, fenced code or `pre` in a code view, and a picture as its words. HTML's other tags are passed over with their words kept; scripts and styles are left out. Nothing is fetched.

## Suggestions under a text box

Keep a `complete::Complete` in your state and show it with `c.view("city", "City", &all, Msg::City)`; give each `complete::Did` to `update(did, &all)`, which returns true when a suggestion was taken into the box. Under the box, in the page and never floating, is a list of up to eight suggestions that start with what is typed, then those that hold it, the typed part marked. Down and Up go round them while the keyboard stays in the box (`Node::on_up_down` on any `entry`), Enter or a press takes one, and Escape puts the list away until something more is typed. `all` is a `&[String]`, or the rows of a `ListModel<T>` through `complete::from_model(&model, |t| t.name.as_str())`, which builds no strings and offers only the rows the model shows. A screen reader hears a combo box, the list's options with the lit one selected, and how many suggestions there are as they change.

## Right-to-left writing, figures and dates

Words in Arabic, Hebrew and other right-to-left writing are shaped and ordered by the text engine, and a line whose first letter with a direction reads right to left starts at the right of its box (a label, rich words, a text box). In a text box, a label's picked words and a text area, Left and Right move the caret the way the arrow points: in right-to-left words Left goes on to the next letter. A selection across both directions is washed band by band over what it holds. `edit::right_to_left(text)` says which way a text reads.

`lang::format::number` and `decimal` write the language's own figures (`kit-number-digits`, ten figures nought first; Arabic and Bengali have theirs) with its decimal and thousands marks, and so do sizes. Which figures are used follows the Unicode CLDR by language and region (`lang::numerals`): Eastern Arabic (U+0660 to 0669) for ar and the regions that use it (ar-SA, ar-EG, ar-IQ, ar-SY, ar-JO, ar-LB, ar-SD, ar-YE and so on), 0 to 9 for ar-MA, ar-DZ, ar-TN, ar-LY, ar-AE and ar-EH, Persian (U+06F0 to 06F9) for fa and ps, Bengali for bn and as, Devanagari for mr and ne, Burmese, Dzongkha; hi and ur use 0 to 9 by default (ur-IN Persian), every other language 0 to 9 unless its file sets `kit-number-digits`. The person's choice is `Numerals::Auto` (the region's rule), `Latin` (0 to 9) or `Native` (the language's own: hi gives Devanagari, ur Persian). A program keeps it with `Numerals::read(&config)` and `save(&config)` (key `numerals`), answers `Host::numerals()` (`Some("auto" | "latin" | "native")`, read on every write so a change shows at once) and puts `settings::numerals_row(chosen, Msg::Numerals)` on its settings page. For one field in 0 to 9 (a phone number, a code, a price) use `Spin::new(..).latin()`, wrap the call in `lang::numerals::latin(|| ..)`, or pass `spin::number_text` to `spin_with`; `Mask::Phone` and `Mask::Date` always keep 0 to 9. Typed text is read in either set or a mix: `numerals::latin_digits(text)` turns figures of any script into 0 to 9, `numerals::digit_value(c)` reads one, and `numbers::read`, `Spin`, `TimeBox`, `DurationBox`, `Date::parse` and the segmented time all use them. Chart words and spin boxes write the language's figures, and the screen reader is given the same text.

`numbers::percent(share, places)` follows `kit-number-percent` ("45%", "45 %", "%45"), and `numbers::read(text)` reads a typed number back: the language's figures or 0 to 9, its marks, or a full stop when that is not its thousands mark. `when::Date::written(Pattern::Full)` and `when::Time::written()` write a date and the clock in the language's pattern and figures.

## Which drawer draws a window

`ui::drawn_by(DrawnBy::Auto | Processor | Gpu)`, called before the first window opens, says which drawer this program's windows ask for. `Auto` is the toolkit's choice: the graphics chip when every check passes, else the processor. The environment wins: `TRINDLE_DRAWN_BY_PROCESSOR=1` forces the processor, `TRINDLE_DRAWN_BY_GPU=1` asks for the graphics chip. `Gpu` still runs every check and falls back to the processor with a reason. Each window prints `trindle: <program> window drawn by <gpu|processor> (<why>)` on standard error when it opens (why: `Asked`, `NoDmabuf`, `NoLibraries`, `NoNode`, `NoContext`, `Software`, `SelfTest`, `Failed`, or `Passed` for the graphics chip); `Shown::drawer()` returns `Drawer::Gpu` or `Drawer::Processor(Why)`, and `Drawer::line(program)` the same line. `TRINDLE_GPU_LOG=1` adds the drawer's events. Atlases start at 512 x 512 and double to 2048 x 2048 before being emptied; while every window is hidden or minimised the buffers, atlases and context are freed and made again on show.

## Drawing on a Painter

A `Painter` records drawing in pixels as a list: `fill`, `round` (a radius for each corner), `line`, `fill_path`, `stroke_path`, `push_clip` and `push_layer` up to `pop`, and `pixels(at, |canvas| ..)` for code that still wants a canvas. `play(canvas)` draws the list, byte for byte as drawing straight onto the canvas would. Each paint function that takes a canvas has a version that takes a `Painter`, and the canvas one (but for `put_frame`, which stays pixels) now records and plays through it: `cellgrid::paint_cells_on`, `term::paint_term_on`, `kanban::paint_board_on`, `tabs::paint_tabs_on`, `table::paint_table_on` and `paint_column_drop_on`, `icongrid::paint_icons_on`, `crop::paint_crop_on`, `spelling::squiggle_on`, `pill::paint_pill_on` and `float_shadow_on`, `ui::fill_on`, `ui::tip_box_on` and `label_pill_on`, `scene::Scene::paint_on`, `rich::Flow::draw_on`, `editing::editor::Pane::paint_on` and `rect_on`, and `widget::put_frame_on`. Those that measured the canvas take its size in pixels. `tiles::Sketch::fit_on`, `strip_on` and `placed_on` make a sketch that records. Words, icons and anything a fill cannot say (gradients, the strokes of a `Way`, clipping to a shape, a sketch's shadows, vector pictures) are recorded as `pixels` for now.

## Painting your own grid (a terminal)

`drawing(size, tip, paint)` gives a canvas, and `paint` gets a `Pen` with the window's `fonts`, `theme` and `scale`. What a program that draws a grid of cells, such as a terminal, can use (see `examples/cells.rs`):

| Need | How |
|---|---|
| The fixed-width font | `Style::monospace(size)`, or `Style { family: Some("monospace".into()), .. }`. `Fonts::monospace()` names the family: the person's own fontconfig monospace font if installed and fixed width, else the built-in Noto Sans Mono (with box drawing). `Harness` and the toolkit's own tests always use the built-in one. A program that lets the person choose names another family in `Style::family` |
| The size of a cell | `fonts.cell_size(&style)` gives `(width, height)` in pixels: the advance of "M" and a line's height |
| Wide characters on two cells | `trindle_toolkit::grid::cells(text)` and `cell_width(char)` give the cells a text or character takes (0 for a joining mark, 2 for CJK, Hangul, fullwidth forms and emoji). `fonts.layout(text, &style, None).snapped(text, cell)` moves each character onto its own cells, so columns line up whatever the font's own widths are. A program that already knows its columns (a terminal emulator's grid) uses `snapped_to(cell, columns, column_of_byte)` |
| The keyboard on open, no click first | `.on_keys(f).first()`. `.first()` gives the drawing the keyboard when the window opens |
| Keys, and text from an input method | `.on_keys(f)` hears `Input::Key`, `Input::Composed` and `Input::Focus`; `None` from `f` leaves the key to the window |
| Copy from a shortcut | In `on_keys`, send a message for Ctrl+Shift+C; in `update` set the words aside; `App::to_clipboard` hands them over (take them out of your state, so they go once). It is asked after every message and every `Shown::change`. The right-click `MenuRow::copy` writes to the same clipboard |
| Mouse selection | `.on_pointer(f)` hears `Pointer::Down`, `Move`, `Up` (also while the button is held outside the drawing), `Hover`, `Leave`, `Middle` and `Menu`, in points from the drawing's corner. Work out the cells yourself and paint the selection |
| Scroll-back | `.on_scroll(f)`: `f` is told lines, down positive (a wheel notch is 3 lines; a touchpad gives fractions, 24 points to a line, so keep the remainder). Use it on a drawing that is not itself inside a `scroll` area |
| Paste from a shortcut | In `on_keys`, send a message for Ctrl+Shift+V; in `update` set a flag; `App::wants_paste` hands the wish over (take it out of your state, so it is asked once) and `App::pasted(text)` receives the text and may answer with a message for `update`. The toolkit reads the clipboard only while the person's own key press is being handled (a key the compositor named as theirs, where it names them): a wish formed on a click, a timer, `Shown::change` or from the program's own output is refused, nothing is read, and the window says why ("Only your own press works here."). It reads at most 1 MB, and only text. The text arrives as it is, control characters included: a terminal must wrap it in bracketed paste or clean it before it reaches a shell |
| A bell | `App::wants_bell`, asked after every message and every `Shown::change` (take it out of your state, so it rings once): the window's edge flashes in the highlight for `--trindle-bell-time` (250 ms by default, 100 to 1000), as wide as the glow. No sound and no pop-up. At most three flashes a second whatever the program asks, and where the person has asked for no movement (`Host::moving` false) the edge appears and goes with no fade |
| The window's title from the program | `App::window_title`, asked after every message and every `Shown::change`; `Window::set_title` does the same by hand |
| Output from another thread | `Loop::every` with `Shown::change_if` (or `Shown::change`) lays out and paints again only when something changed |

Speed: laying out a screen of 3,000 cells as 50 rows of one run each, snapped to the grid, takes about 1.5 ms, and painting it about 1 ms more (release build, `grid::tests::a_screen_of_3000_cells_is_laid_out_in_time`, run with `--ignored --nocapture`). Laying out each cell on its own takes about 30 ms, which is too slow for a frame, so lay out one run per row, or per stretch of one colour, and not per cell. No layout cache is kept because the measured cost does not call for one.

Not offered: an X11 back end.

### A screen of cells: `cellgrid`

A terminal does not have to lay out cells itself. `cellgrid::Screen::new(cols, rows)` holds `Cell`s (words, `fg`, `bg`, bold, italic, underline, strike, inverse); `put(col, row, text, &look)` puts text one character to a cell, a wide character on two with a spacer after it and a joining mark on the cell before. Size the grid with `cell_metrics(pen, size)` (one cell in points). Paint it in a drawing with `cellgrid::paint_cells(canvas, pen, &screen, size, caret, selection)`: backgrounds filled in runs, words laid out one run to a stretch of one look, the cursor (`Caret` as a block, bar or underline; only an outline when the window lacks the keyboard) and the selection (`Selection`, stream or block; `words(&screen)` gives what to copy) drawn over. Tell the screen reader with `Node::reads`.

## Drag and drop with other programs

Files and text come and go on their own: a text box takes text, `Node::on_drop_from_outside(would, take)` lets any widget take files or text, and `App::dragging` gives the files a program holds. For data of a program's own kinds, named by mime type, both ends are one call. To drag it out, fill `Lifted::typed` with `(kind, bytes)` pairs, the best first; they are offered before any files or text, and each is sent as it is asked for. To take it in, `Node::on_drop_of(&["image/png", "application/x-card"], would, take)`: the widget is lit only while one of its kinds is offered, the first of its kinds that is offered is the one asked for, and `take` is given `Given::Typed(kind, bytes)` (no more than `dnd::MOST_BYTES`) or `Given::Nothing(why)`. While something held would land on a widget, the screen reader hears that widget described as "Drop target".

## What a screen reader is told

Every window publishes an AccessKit tree (roles, names, values, states, actions) while a screen reader is listening, and costs nothing while none is. Most of it comes from the widgets themselves; these are the parts a program can add to, all on `Node`:

- `called(name)`: the name of a picture or ring that shows none. Rings are named "Progress" unless you say.
- `role(Role::..)` and `value(words)`: the one way to tell what a `drawing` or group is (`role::Role`: a button, a check box or switch with whether it is on, a slider, spin button or meter such as a gauge with its value, least and most, an image, a group, a dialog, a menu bar, a toolbar, a status line, a path, a two-handled slider or a box of segments) and the words read as its value. The reader steps a slider or spin button that takes keys by sending it Up and Down. See [docs/guides/custom-widgets.md](guides/custom-widgets.md).
- `polite()`, `assertive()`, `alert()`: words that are spoken when they change, once the reader is free, at once, or as an alert. Words in the problem tone (`Tone::Problem`) are told as alerts without asking.
- `busy()`, `progress(share)`: a spinner and a ring are busy while they work; `progress(Some(0.4))` or `progress(None)` makes a `drawing` a progress indicator with a value (the standard ring does this).
- `reads(Reading { lines, caret, selection })`: a `drawing` that paints text (a terminal) publishes its visible lines, the caret and the selection, in letters. The lines are told as they are, so never give it what a person typed into a secret box.
- `menu_rows(rows)`: a `drawing` that paints a menu publishes each row with "3 of 12" and the lit row as the one the keyboard is on (`popup` does this).
- `dialog_message()`, `alert_message()`: put on the label holding a dialog's message; the window is then told as a dialog (or an alert dialog) with that message as its description, after its title.

List rows, the options of `choice` and menu rows publish their place in the set and the set's size. A secret entry is always a password box to the reader and its characters are never published, even while its eye is on and they show on screen.

- `landmark(Landmark::Main)` (or `Navigation`, `Beside`, `Search`, `Form`, `Top`, `Foot`, `Region`): one of the window's big parts a reader jumps between; with `called(name)` it is told by that name.

A ring is a progress indicator; with `polite()` its progress is also spoken as it moves.

For tests (the `testing` feature): `Ui::unnamed_controls()` returns every control with no role or no name, and `Ui::kept_from_a_reader()` every part a reader could not reach. With the feature on, every view a test paints is checked the first time it is painted, so any window with a picture test also holds to the rule; `TRINDLE_AUDIT=off` skips it and `TRINDLE_AUDIT=report` prints instead of failing.

## Words or icons on buttons

Buttons are plain icons that show a soft square when pointed at or on, with the words as the label that shows on pointing. Nothing is a pill: every button, strip, tab, chip, switch and label has the one corner `--trindle-corner` (8 points); only the ring is round. Use words only where an icon would leave the meaning to be guessed: `main_word("Save")` for the one main action on a screen (Save, Replace), and `word_button` for a choice such as Dark or Light. Every other button is `button(icon, tip)`. The `tip` is required: it is the label on pointing and the name the screen reader speaks. Icon names are looked up in the person's icon theme; a name that is not found draws a stand-in.

## Units

A window's size is in points: logical pixels, which the toolkit multiplies by the screen's scale (1.0, 1.5, 2.0 and so on). `Shown::open(.., (360, 240), ..)` is the same size on every screen. Padding, gaps and sizes in the widgets are points too.

## App ids

`Kind::Window { title, app_id }`: the `app_id` is how the desktop knows your program, for its icon and for matching a launcher entry. Use a reverse-domain name you own, in the same spelling as your `.desktop` file without the extension: `org.example.Notes`, `com.yourname.Names`. Keep it the same between versions and different from every other program's.

## Read-only lists

`list` asks for a `choose` closure that returns one of your messages. For a list that is only read, give it a message that does nothing and leave `chosen` as `None`:

```rust
enum Msg { Nothing }
// in update: Msg::Nothing => {}
list(rows, None, |_| Msg::Nothing)
```

The `names` example does this.

## Shapes, gradients, clipping and shadows in a sketch

A `tiles::Sketch` draws in its own units. `tiles::Way` is a free shape in those units: `Way::new().move_to(x, y).line_to(..).quad_to(c, to).cubic_to(c1, c2, to).close()`, or `Way::rounded((x, y, w, h), radius)` and `Way::circle(at, r)`. `fill(&way, &fill)` and `stroke(&way, width, &fill, dash)` take a `tiles::Fill`: `Flat(colour)`, `Linear { from, to, stops }` or `Radial { centre, r, stops }`, stops running from 0 to 1. `dash` is the lengths drawn and left in turn (`&[]` for a whole line); strokes have round ends and corners. `clipped(&way, |s| ...)` keeps everything drawn inside the closure, words and pictures included, inside the shape. `shadow(&way, by, blur, colour)` lays a soft shadow of the shape moved by `by`; draw it before the shape. `vector(&tree, box)` draws an SVG at the sketch's size. `Sketch::placed(canvas, pen, k, at)` makes a sketch of `k` pixels to the unit with its top left at `at`, for a drawing a program places and zooms itself.

## A scene of items to move and zoom

`scene::Scene` holds `scene::Item`s (`Item::new(name, at, size, |s| draw)`, `.fixed()` for one that cannot be moved), each drawn by its own sketch in its own units; later items lie over earlier ones. Paint it in a `drawing` with `scene.paint(canvas, pen, &view)`, using a `zoom::View` for zoom and pan. Give the drawing's pointer to `scene.pointer(&mut view, event)`: a press chooses the item under it, a drag moves it in scene units at any zoom, and a drag on nothing pans a zoomed view. `scene.key(&mut view, sym, mods)` gives Tab and Shift+Tab through the items, arrows to move the chosen one (ten units with Shift), plus, minus and 0 to zoom. Each returns a `scene::Change` (`Chosen`, `Moved`, `Looked`) so the program repaints. `hit(&view, x, y)` finds the top item under a point. Give the drawing `scene.told()` as its name for a screen reader; the chosen item is ringed in the highlight with the sheet's focus width.

## Vector pictures at any size

`vector::vector(tree, size, tip)` is a node that draws an SVG from its shapes at whatever size it is shown, so it stays sharp when zoomed or on a sharper screen; `vector::draw(canvas, &tree, rect)` draws one into a box keeping its shape. Read the tree with `picture::svg_tree(bytes)`, which follows nothing the SVG names.

## A video or sound player

`player::Player::new(length, frames)` keeps the state (`Stopped`, `Playing`, `Paused`, `Ended`), how far in, the volume and mute; the program does the decoding. Fill in `player::Decoder` (`play(from)`, `pause()`, `seek(to)`, `volume(level)`) and pass it to `update(control, &mut decoder)`. Report back with `reached(at)` as it plays and `ended()` at the end, and put each video frame in the `Frames` given to `new` from the decoding thread, then call `Window::patch` to show it without painting the rest. `view(size, name, wrap)` shows the picture and a row of controls: play or pause, back and forward 5 seconds, the time, a bar to seek along (left out for a stream with no end), mute and volume. `Player::key(sym, mods)` turns Space, K, J, L, the arrows and M into controls for a program to pass on.

## A surface the program draws into with the GPU

`Window::gpu_surface(at)` makes a Wayland subsurface of the window, `at` points from its top left, which runs free of the window's frames: the program attaches and commits its own buffers. `surface()` and `connection()` are what EGL, Vulkan or a video decoder need; with the toolkit's `gpu` feature (on by default; it links libwayland-client), `display_ptr()` and `surface_ptr()` give the raw `wl_display` and `wl_surface` pointers, valid while the `GpuSurface` lives. `place(at)` moves it, `below()` puts it under the window's picture for a program that leaves a see-through hole for it, and dropping it removes it. Pointer and touch pass through it to the window. Tested against a stand-in compositor, not yet with a GPU.

## Fonts to choose and which font draws what

`Fonts::chooser()` lists every family on the computer by name with its faces (weight and italic), whether it is fixed width and whether its letters are coloured pictures, as emoji fonts are. `Fonts::fallbacks(text, style)` says which family draws each run of the words: the chosen one, or the stand-in found for letters it lacks (emoji come from a colour emoji font when one is installed), and None for letters no font has.

## Spell checking a text box

Fill in `spelling::Speller` (`known(word)`) from the program's dictionary and add `.spelling(&speller)` to an `entry`. Each word of letters it does not know gets a wavy line under it in the sheet's `--trindle-spelling` colour, never red, as thick as the caret, and a screen reader is told the box has spelling mistakes. A secret box is never checked. `spelling::misspelt(text, &speller)` gives the ranges for a program that marks words itself.

## Work on threads and timers

`tasks::Tasks::new(&events, deliver)` hands messages to `deliver` on the loop's thread; for a window `deliver` is usually `move |m| shown.change(|app| app.update(m))`. `spawn(work)` runs `work` on a thread and delivers what it returns, `spawn_sending(work)` gives the thread a `Post` to send as many messages as it likes, `spawn_catching(work, failed)` and `spawn_sending_catching(work, failed)` do the same and deliver what `failed` makes from the words of a panic if `work` panics, so a program waiting for the answer is not left waiting, `after(wait, make)` delivers once, and `every(every, make)` delivers until the returned `Timer` is stopped or `make` gives `None`.

## A live view of a folder

`watch::live(&events, folder, changed)` watches a folder on the loop: `changed(paths, again)` is given the files and sub-folders made, written, moved or removed, and `again` is true when news was lost or the folder itself went, so the whole folder should be read again. Watching stops when the returned `Live` is dropped. `Watch::with_subfolders()` makes a plain watch hear sub-folders too.

## Open with and recent files

`open_with::apps_for(&Places::of_this_desktop(), mime)` lists the installed apps that open a kind of file, the person's default first, read from the desktop files and mimeapps.list as the XDG specifications say (the person's own copy of an app wins, hidden apps and removed associations are left out). `App::command(files)` fills in the desktop file's `%f`, `%F`, `%u` and `%U`, each file one word, never through a shell. `open_with::set_default(places, mime, app)` saves the person's choice; `open_with::chooser(apps, chosen, choose)` is the list to pick from. `open_with::recent(places)` reads recently-used.xbel and gives the files still there, newest first, with their kind.

## A crash and error page

`crash::install(folder, program, version)` makes a panic write a report (program, version, time, system, what, where and the trace) to `crash.txt` in `folder` before the program ends; `crash::take(folder)` gives it once at the next start. `crash::Report::new(program, version, what)` is a report for a fault the program met itself, and `text()` is the report as plain lines. `crash::page(program, report, copy)` shows what happened in plain words, the report, and a "Copy report" button that sends `copy`; put the report on the clipboard with `App::to_clipboard`.

## Naming notes

- `title(text)` and `page_title(text)` are headings drawn inside the window. The window's own title, shown in its title bar, is `title` in `Kind::Window { title, app_id }`. They are unrelated.
- `button` takes an icon name first; `main_word` and `word_button` take words only.
- `tip` is the name of a widget for the label on pointing and for the screen reader. On `entry` it also shows faintly while the box is empty.
- `Msg` must be `Clone`.

## The style sheet

The look is one style sheet, `share/style.css`, built into the crate. On Trindle, the person's theme, light or dark, highlight colour and own sheet in `~/.config/trindle` are laid over it. Anywhere else, the built-in sheet and its yellow highlight are used.

More about what the toolkit took from Trindle and what it needs for a terminal is in `docs/toolkit-library.md` in Trindle's repository.

## Controls, actions and data

Each is its own module; the state kinds are held by the program and changed by `update`, as `picker::ColourBox` and `when::DateBox` are.

| Module and builder | What it is |
|---|---|
| `action::Actions`, `Action::new(id, words).icon(..).keys("Ctrl+S")` | Named actions with words, an icon, a shortcut and whether each can be done now. `find(input)` gives the enabled action a key press stands for; `menu(ids, wrap)` gives menu rows (one that cannot be done is left out); `toolbar(ids, wrap)` a row of round buttons (one that cannot be done is greyed); `search(query)` what the palette lists. A shortcut two actions would share is refused |
| `palette::Palette` | The command palette: a box and the actions matching every word typed, those starting with it first. Enter runs the chosen row, a click or Enter on the list runs that one, and running empties it. It is a page, not a float: show it in place of the page |
| `validate::CheckedBox::new(Mask::Phone \| Date \| Hex, text)` | A box that drops what cannot be in it (adding nothing, so the caret stays put), then, once the keyboard has left it, says what is wrong in red words in a line kept under it, so the page never moves. The screen reader hears the box as invalid with the words as its error |
| `dial::dial(value, min, max, step, tip, change)` | A round dial (48 points) dragged round, wheeled, or moved by arrows, Page Up and Down, Home and End; a screen reader hears a slider. Track, fill and knob are the slider's sheet values |
| `dial::level_bar(value, min, max, tip)` | How full something is, as a bar with the slider's track and corner; heard as progress |
| `dial::scale(value, min, max, step, marks, tip, change)` | A slider with words under it at the values `marks` gives |
| `dial::volume(level, muted, mute, change)` | A mute button whose icon follows the level, and a slider beside it; nothing pops up |
| `buttons::colour_button`, `font_button`, `file_button`, `lock_button` | Buttons that show what they hold: a colour swatch (heard with its code), a font's name and size, a file's name or "Choose a file", and a lock over settings. The press is the program's, such as showing a `picker::ColourBox` or asking `chooser::open`. A link's button is `widget::link` |
| `spin::spin(value, min, max, step, tip, change)`, `spin_with` | A number between Less and More buttons (greyed at the ends); the number takes the arrows, Page keys, Home, End and the wheel, heard as a slider |
| `spin::time_spin(time, change)`, `spin::month_year(year, month, change)` | A time as two spin boxes in two figures; a year spin over the twelve months as word buttons |
| `segments::SegmentedTime::new(time)` | A time in one box as two segments, hours and minutes, in the sheet's typing box with the lit segment in the highlight: `picker.node(name, Msg::Time)` and `update(SegMsg)` (true when the time changed). Left and Right, and Tab on the way through, take a segment; Up and Down step it going round (23 to 0, 59 to 0), Page keys by six hours or ten minutes, Home and End to its ends, figures type into it (a figure too big for a first one goes in whole, and two are held to the most) and a press takes the nearer segment. The screen reader hears a group of two spin buttons with Increment, Decrement and Focus. |
| `rows::toggle_row`, `combo_row`, `entry_row`, `spin_row` | Settings page rows: a `settings::setting` holding a switch, dropdown, text box or spin box named by the row |
| `dock::Dock` | Panels round a main area, at the left, the right, the foot or floating at its top right, moved by the buttons on each head or by dragging the handle on it (a line in the highlight shows the edge it would land on, `dock::edge_for`). `view(main, body, wrap)` sends `dock::Change`s; hand each to `Dock::update`, which returns the `Moved` panel, if any, for the program to keep |
| `toolbox::toolbox(tools, chosen, choose)`, `toolbox::tab_pages(names, chosen, tip, choose, page)` | A grid of tool buttons with the one in use on; a row of tabs over a page, which may hold tabs of its own |
| `info::info_panel(kind, words, buttons)` | News in a card in the page, in place of a banner or toast: Note, Done, Warning or Failed (the only red one). Spoken as it appears, a failure at once |
| `model::ListModel` | The program's things shown sorted (`sort_by`), filtered (`filter`) and grouped (`group_by`, `groups`), changed by `push`, `remove` and `edit`; `take_changes` says what changed row by row (`Inserted`, `Removed`, `Changed`, `Reset`) |
| `form::Form` | A form tied to a record: `.text(name, get, set)` and `.number(..)` fields read from it by `load` and written back as typed when right; a field that is wrong keeps its text and shows red words under its box |

Words that change with a number use the plural forms of the language file's own rules (`share/lang/README.md`, "Plurals"): English, Polish, Russian and Arabic are tested with every form they have. Words that change with gender are chosen by a `[male]` / `[female]` / `*[other]` selector on a variable given as `gender = Gender::Female` (`lang::Gender`), alone or inside a plural choice; a language with no gendered words may leave it out, and one with them may add it where English has none.

## Tools for program authors

- **Inspector.** Ctrl+Shift+F12 in any window (or `Ui::inspect(true)`) draws an edge round the widget under the pointer and, under it, its kind and key, its size and place in pixels, its state (keyboard, pointer, pressed, takes the keyboard, cannot be used), what the screen reader is told, and the sheet values that shape it. `Ui::inspected()` gives the same lines to a test.
- **Speed overlay.** Ctrl+Shift+F11 (or `Ui::show_speed(true)`) shows in the top right corner how long the last frame took to paint, the memory the program holds and the share of the window painted again. `Ui::speed()` gives the lines.
- **Style sheet hot reload.** Saving `~/.config/trindle/style.css` shows the change in every running window at once, as before; the sheet is also checked and each problem is written to the program's standard error in plain words (`theme::lint::log`), never on screen, as a sheet half written is saved often.
- **Style sheet checker.** `trindle-sheet-check [file.css ...]` (by default your own sheet and themes) fails when a number is outside the limits written beside it in `share/style.css`, or a colour the sheet sets stands below its WCAG 2.2 AA floor (4.5 to one for words, three to one for edges and marks) on anything it is drawn on, in each look the sheet has. `theme::lint::lint(css)` is the same check for a test.
- **Test harness.** `testing::Harness` (feature `testing`) drives a program's window with no desktop: click by screen reader name, type, press keys, read the words shown, take a picture. See [the testing guide](guides/testing.md).
- **New program.** `trindle-new <name> [--toolkit <path>]` writes a folder with a window (`src/lib.rs`, `src/main.rs`), a style sheet, an English language file and a test, from `share/template`. The toolkit's own tests build and run the template, so a new program always compiles and passes.
- **Widget gallery with its code.** `showcase::page()` (`cargo run --example widgets`) shows every common widget beside the code that makes it, taken from the same lines by `stringify!`, so the two cannot differ.
- **Language check.** `trindle-lang-check` also fails on a plural line for a form the language never gives (`[few]` in English, `[one]` in Japanese), which would never be shown. Unused English words and missing plural lines were already problems.
- **Guards in the tests.** `src/unsafe_tests.rs` counts every `unsafe` against an audited ledger, file by file, and fails on any outside the sys modules. `tests/budgets.rs` fails when a small window takes more than 50 ms of processor time from nothing to its first frame, or the hello example grows past its size budget. `src/ui/zero_config_tests.rs` holds a sample program written with plain widget calls to every control named, with a role, reached by Tab in reading order and drawn with the keyboard on it. `src/ui/scale_tests.rs` checks every quarter scale from 1.0 to 4.0: widgets on whole pixels and words on whole pixels, and the same window painted twice gives the same picture.
